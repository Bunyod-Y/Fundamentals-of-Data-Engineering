## Scenario

A claims clearinghouse drops newline-delimited JSON claim files and a CSV provider file into a UC volume
landing folder. Files keep arriving; later files add a new column (`payer`) and one file has a bad value
(`claim_amount = "N/A"`).

## Warm-up (recall L02, no hints)

- W1 schema evolution on append (`mergeSchema`)
- W2 CHECK constraint rejects a bad row
- W3 DEEP CLONE is independent of its source

## Examples

- E1 read_files on JSON: inferred types, `_metadata.file_name`, row count per file
- E2 CSV: `spark.read.csv` without options vs `read_files` (header + type inference) + `schemaHints`
- E3 COPY INTO: schemaless target + mergeSchema, rerun is idempotent, new file loads only the new rows
- E4 Auto Loader basics: cloudFiles + schemaLocation + availableNow; types without inferColumnTypes;
  second run with no new files; third run after a new file; `cloud_files_state`
- E5 Schema evolution (addNewColumns): new column stops the stream (real error class), restart adds it;
  `_schemas` folder versions
- E6 Rescued data: type mismatch -> NULL + `_rescued_data`; `schemaEvolutionMode = rescue` keeps the
  schema and puts the new column in `_rescued_data`

## Evidence from test runs (outside _authoring/L06.json)

- Run 771734934782354 (2026-10-21, E5 written with try/except around the stream in the lesson notebook):
  the job failed with `ERROR: Some streams terminated before this command could finish!` although the
  exceptions were caught. The caught errors were `[UNKNOWN_FIELD_EXCEPTION.NEW_FIELDS_IN_RECORD_WITH_FILE_PATH]`
  (new field `payer`) and, on restart without writer mergeSchema, `[DELTA_METADATA_MISMATCH]`.
- Probe run 188792106301462: `spark.streams.resetTerminated()` after the caught failure does not prevent it.
- Probe run 1033769113277394: the same failing stream inside a child notebook called with
  `dbutils.notebook.run` -> the parent catches `Py4JJavaError` (`com.databricks.WorkflowException`), its cell
  survives, and a restart through the child loads the new column.
- Design consequence: runs A and B of E5 are cells marked `# EXPECT_FAILURE: <key>`. The learner sees the real
  error. Test runs execute them through the build harness (a child notebook) and record the error classes.
